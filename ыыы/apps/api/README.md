# ZAL API

FastAPI + SQLite: каталог, геометрия зала, бронь, заказы, Platega и электронные билеты. Общий контракт — `../../contracts/openapi.json`.

Требуется **Python 3.12+**. Системный `python3` на macOS может быть 3.9; он несовместим с этим приложением.

```sh
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt
# Только если .env ещё не существует:
# cp .env.example .env
.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Настройки автоматически читаются из `apps/api/.env`, существующие переменные окружения имеют приоритет. Не заменяйте заполненный `.env` шаблоном. Ключи не нужны фронтенду.

Локальный frontend уже проверен с реальным API на 8000 и `data/zal-integration.db`; команды описаны в `../../docs/deployment.md`. Для параллельной изолированной проверки без настоящих платежей:

```sh
PAYMENT_PROVIDER=mock DATABASE_PATH=./data/zal-integration.db \
PUBLIC_APP_URL=http://localhost:5173 PUBLIC_API_URL=http://127.0.0.1:8001 \
ENABLE_EXTERNAL_MEDIA_NETWORK=0 ENABLE_BACKGROUND_RECONCILER=0 \
.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8001 --no-access-log
```

Этот режим использует настоящий API и SQLite, но sandbox-провайдер платежей; `/api/v1/health` честно возвращает `mode=mock`. Sandbox подтверждения не регистрируются в production или при `PAYMENT_PROVIDER=platega`. Публичный импорт каталога отключён до появления авторизации администратора.

Миграции и seed выполняются при запуске. Общие fixtures содержат 8 матчей, 32 записи расписания и два сектора по 282 места. Заказы, оплаты, токены, цены уже созданных мест и билеты при повторном seed сохраняются. Геометрия обновляется автоматически только для залов без заказов и только при добавлении мест. Зал с существующей бронью сохраняется целиком; изменение его конфигурации требует отдельной миграции. Истёкшее демонстрационное расписание без заказов переносится с сохранением интервалов между матчами.

SQLite-файл и его `-wal`/`-shm` файлы находятся в `DATABASE_PATH`. Для хостинга нужен постоянный диск. Не удаляйте БД ради обновления каталога. Если `ORDER_TOKEN_SECRET` не задан, сервер генерирует и сохраняет его в БД; после рестарта доступ к прежним заказам сохраняется. Настроенный секрет нельзя произвольно менять после создания заказов.

Проверки используют временные БД и фейковые платежи:

```sh
.venv/bin/python -m unittest discover -s tests -v
```

Настоящая оплата требует `PAYMENT_PROVIDER=platega`, приватных ключей, правильного `PUBLIC_APP_URL` и доступной серверной сверки статуса. Callback существующего мерчанта автоматически не меняется. Подтверждение оплаты через redirect или браузерный параметр не используется.
