# Platega SBP и выдача электронного билета

Задача jasperBLCK: реальный платёж по СБП, подтверждение с сервера и ровно один электронный билет на оплаченное место. Клиент получает только ссылку оплаты и безопасное состояние заказа.

## Доступ

Проверка предоставленной пары ключ/merchant выполнена запросом чтения GET /balance/all: результат в [platega-check.json](platega-check.json). Она подтверждает авторизацию, но не доказывает доступность СБП, выпуск платежа или приход callback.

Секреты владельца находятся локально в apps/api/.env с правами 600. Они исключены из Git. Друг получает этот файл от владельца отдельно, не через PR/Issue/коммит. В репозитории только [.env.example](../apps/api/.env.example).

Не выводить значения в логи, исключения и промпты, загружаемые на GitHub. Не использовать PLATEGA_API_KEY на фронте.

## Официальные интерфейсы

Base URL: https://app.platega.io. Авторизация сервера — заголовки X-MerchantId и X-Secret. Значения брать из PLATEGA_MERCHANT_ID и PLATEGA_API_KEY. [Авторизация](https://docs.platega.io/).

Создание: POST /transaction/process. Для СБП в документации используется paymentMethod=2. Сумма paymentDetails.amount передаётся в рублях, currency=RUB. Наша БД хранит копейки: преобразовывать через Decimal, без float-арифметики. Нужны description, return, failedUrl, payload и metadata.user_email. ID транзакции генерирует провайдер. Сохранить transactionId, redirect, status и expiresIn из ответа. [Создание платежа](https://docs.platega.io/создание-платежной-ссылки-с-заданным-методом-29203843e0).

Наш пример сборки тела, не команда для автоматического платежа:

~~~python
provider_body = {
    "paymentMethod": 2,
    "paymentDetails": {"amount": amount_rub, "currency": "RUB"},
    "description": f"Билет ZAL, заказ {order.id}",
    "return": f"{public_app_url}/payment/return?order={order.id}",
    "failedUrl": f"{public_app_url}/payment/return?order={order.id}",
    "payload": order.id,
    "metadata": {"user_email": validated_customer_email},
}
~~~

Если для мерчанта обязателен metadata.userId, хранить постоянный ID покупателя на сервере и отправлять его. Не генерировать новый фиктивный email для каждого заказа. Принимать email через checkout.

Проверка: GET /transaction/{transactionId} с серверными заголовками. Ответ содержит status, paymentDetails, payload и дополнительные поля. Сверять transactionId, привязку к заказу, amount и currency. Не считать redirect или QR доказательством оплаты. [Статус платежа](https://docs.platega.io/проверка-статуса-оплаты-платежа-29203844e0).

### Цена места и итоговая сумма провайдера

При текущих настройках мерчанта провайдер может добавить комиссию покупателю. В реальном запросе на 900 ₽ ответ создания содержал `paymentDetails: "927 RUB"`, а GET — сумму 927 ₽. Это было причиной ошибочного `payment_review` после успешного создания оплаты. Поле `comission` не используется для вычисления доплаты: его смысл и комиссия покупателя могут различаться.

Исходный серверный тариф сохраняется в `payment_attempts.amount_minor`. Точная итоговая котировка из авторизованного POST сохраняется в `orders.total_minor`; она должна иметь ту же валюту и быть не меньше тарифа. GET обязан совпасть с этой котировкой до копейки. Цена места, разница как комиссия и итог показываются до перехода к оплате; билет содержит фактически подтверждённый итог. Не прибавлять на клиенте предполагаемые 3%.

Сохранённый успешный POST позволяет восстановить котировку старого неоплаченного заказа без нового POST. Восстановление проверяет transactionId, валюту, нижнюю границу суммы, отсутствие билета, спора и возврата; затем выполняется текущий GET. Оплаченные и спорные заказы не пересчитываются. Callback до сохранения котировки не выпускает билет; после сохранения выполняется новая проверка GET.

Публичные условия Platega указывают минимум СБП от 1 ₽; доступность конкретной суммы для мерчанта подтверждается только ответом создания. Комиссия может увеличить итог выше 1 ₽. [Условия СБП](https://platega.io/ru/sbp).

## Callback

Публичный адрес нашего обработчика: https://YOUR_DOMAIN/api/v1/payments/platega/callback. Указать его в личном кабинете в настройках Callback URLs. У мерчанта один общий callback: до замены проверить, не используется ли он другим проектом; при использовании подключить маршрутизацию по известным transactionId/payload.

Провайдер требует публичный HTTPS с действующим сертификатом. Проверять X-MerchantId и X-Secret, секрет сравнивать через hmac.compare_digest. Тело актуальной документации — camelCase: id, amount, currency, status, paymentMethod, payload. События могут дублироваться и приходить не по порядку; отвечать 200 после надёжного сохранения/обработки. [Общие правила callback](https://docs.platega.io/колбэки-общая-информация-2499110m0).

Сначала сохранить аутентифицированное событие в payment_events, затем провести проверку через GET статуса и атомарно применить результат. Если внешний API недоступен — событие остаётся в очереди локальной БД, повторяется worker, билет пока не выдаётся.

Не брать старый пример с PascalCase как единственный формат. При необходимости совместимости добавить явные aliases, а конфликтующие значения двух вариантов отклонять.

## Состояния и конкурентность

~~~mermaid
stateDiagram-v2
    [*] --> creating_payment: атомарная бронь
    creating_payment --> pending_payment: ссылка получена
    creating_payment --> payment_review: результат запроса неизвестен
    pending_payment --> paid: статус и сумма проверены
    pending_payment --> canceled: подтверждённая отмена
    pending_payment --> expired: подтверждённое истечение
    paid --> payment_review: спор или частичный возврат
    paid --> refunded: полный возврат подтверждён
    payment_review --> paid: сверка восстановила оплату
~~~

1. В короткой SQLite-транзакции создать order и забронировать session_seat, только если available. Сохранить Idempotency-Key и хеш запроса. Один ключ + одно тело возвращает тот же заказ; другое тело — 409.
2. До сетевого запроса атомарно установить `payment_attempts.request_sent=1`. Только выигравший эту операцию запрос вызывает Platega вне транзакции БД. Это защищает от параллельных повторов одного ключа и рестарта во время POST. Нормальный ответ сохранить до выдачи ссылки клиенту; поздний ответ создания не перезаписывает состояние, уже проверенное через GET.
3. При таймауте после отправки, любом HTTP 5xx, 408/409/429, redirect или неполном успешном ответе POST не повторять автоматически: провайдер мог создать платёж. Сохранить неопределённую попытку и удерживать место. Снять `request_sent` и разрешить повтор с тем же ключом можно только после доказанного сбоя подключения до отправки или явного отклонения запроса. Без transactionId выяснять результат по кабинету/событию; не создавать второй платёж вслепую.
4. Для CONFIRMED сверить авторизацию callback, данные провайдера и сумму. В одной транзакции paid + sold + UNIQUE(order_id) ticket. Повторный callback и одновременный polling не выпускают второй билет.
5. CANCELED/EXPIRED освобождают бронь после достоверной сверки. Возврат пользователя по failedUrl лишь запускает проверку.
6. Таймер брони основан на expiresIn, но сам не освобождает место. Пока состояние банка неизвестно — held, интерфейс сообщает о проверке.
7. При DISPUTED/частичном возврате приостановить билет (suspended), сохранить место sold до решения. Полный подтверждённый возврат — revoked/refunded; автоматическую повторную продажу этого места в прототипе не делать.
8. Старое CANCELED после paid не должно откатывать покупку. Проверять текущее состояние провайдера; для возвратов учитывать refundId и успешность операции. [События по платежам](https://docs.platega.io/вебхуки-по-платёжным-ссылкам-2506212m0).

Если неизвестный transactionId приходит с payload нашего существующего заказа при потерянном ответе создания, проверить GET провайдера и связать попытку атомарно. Никогда не создавать новый заказ только из payload внешнего события.

GET должен вернуть тот же идентификатор транзакции, точный `payload=order.id`, исходную сумму и валюту. Если провайдер возвращает merchantId/mechantId и paymentMethod, они также проверяются. Отсутствующий payload или валюта не заменяются значениями по умолчанию. Суммы с долями копейки, NaN и Infinity отклоняются. Заголовки мерчанта не пересылаются при HTTP redirect.

Worker опрашивает незавершённые и оплаченные заказы, поэтому подтверждение оплаты и обнаружение возврата работают без смены callback существующего мерчанта. Один процесс API сериализует проверку одного заказа; production запускается с одним uvicorn worker. Очередь и привязки переживают рестарт в SQLite. Неизвестный результат POST без transactionId невозможно опросить: такой заказ остаётся на проверке до события или ручного разбора в кабинете.

В актуальном callback сумма одной операции возврата называется `refundAmount`, а результат — `refundStatus=Succeeded` либо `Declined`. `refundAmount` нельзя считать накопленной суммой всех возвратов. Callback только запускает проверку: билет меняется по текущему GET, а поля старого уведомления не переопределяют его результат. Подтверждённый PARTIALLY_REFUNDED сохраняет suspended даже после более позднего CONFIRMED; полный CHARGEBACKED необратимо отзывает билет. DISPUTED может восстановиться после подтверждённого разрешения спора. [Возвраты Platega](https://docs.platega.io/chargebacked-40030962e0), [результаты операций](https://docs.platega.io/результат-операции-возврата-18505516d0).

## Билет

Генерировать ticket.id и отдельный случайный token минимум 128 бит. QR ведёт на PUBLIC_APP_URL/tickets/{token}; страница запрашивает GET /api/v1/tickets/{token}. В QR нет API-ключа, email или токена приватного заказа.

Данные: стадион, матч, зал, дата/часовой пояс, ряд/место, сумма, номер заказа/билета, статус. Печатный вариант через CSS @media print достаточен для P0; отдельный PDF — при наличии времени.

GET order и order/ticket требуют access_token заказа. Проверка QR публична только для обладателя непредсказуемой ссылки и возвращает минимальные данные без email. На API/страницах с токенами отключить стороннюю аналитику и поставить Referrer-Policy: no-referrer.

Билет приложения относится к демонстрационному матчу. Для реального прохода в сторонний стадион потребуется интеграция с его продажами и контролем входа.

## Обязательные проверки

До production проверить на заглушке адаптера: duplicate callback, одновременные подтверждения, неверный секрет/сумма/валюта, таймаут POST, поздний CONFIRMED, callback до ответа создания, рестарт API, спор/возврат, повтор Idempotency-Key.

Из корня репозитория: `PYTHONPATH=apps/api apps/api/.venv/bin/python -m unittest discover -s apps/api/tests -v`. Платёжные проверки в `apps/api/tests/test_payments.py` используют временную SQLite и httpx.MockTransport; ключи из .env не читаются, обращений к живой Platega нет.

Затем вручную на реальном мерчанте: создать согласованный заказ, оплатить в банковском приложении, увидеть CONFIRMED и один билет, обновить страницу и повторно открыть QR. Сумму и факт расхода подтверждает человек; CI не создаёт и не оплачивает реальные транзакции.

Промежуточный тест авторизации не заменяет этот проход. Не заявлять реальную интеграцию готовой до него.

## QR оплаты на странице заказа

Прямой банковский URI берём из `qr` в авторизованном [GET статуса](https://platega-io.gitbook.io/platega.io-api-dokumentaciya/api-docs/images-and-media). Разрешён только HTTPS `qr.nspk.ru`; ключи и сырой ответ остаются на сервере. После проверки транзакции URI сохраняется в `payment_attempts.qr_url` (аддитивная миграция). В браузере `qrcode` создаёт PNG с белой зоной вокруг кода; доступно сохранение PNG. Форма Platega открывается в отдельной вкладке. Опрос продолжается каждые 3 секунды (при ошибках до 10), при подтверждении открывается билет. Код не отображается для paid/review/canceled/expired/refunded и при истёкшем локальном сроке.

Проверки этого изменения: 68 backend-тестов, включая сохранение QR после повторного открытия БД, недопустимые URI, несовпадающую сумму и получение ровно одного билета через polling. Реальный GET на существующей транзакции вернул `qr.nspk.ru`; на сервере обнаружен один подтверждённый заказ с действующим билетом. Новые списания при разработке не выполнялись.

### QR до открытия платёжной формы · 07.11.2026

На новом реальном заказе авторизованный GET вернул PENDING и `qr: null`, хотя ссылка `pay.platega.io` уже существует. Простое открытие HTML формы не создаёт банковский QR; в интерфейсе провайдера есть отдельная инициализация метода. GET `/transaction/{id}/qr` в этом состоянии вернул 400 (QR unavailable), а `/v2/transaction/{id}/set` с заголовками мерчанта — 403. Обход авторизации или копирование внутренних подписей payform не реализованы.

Вместо бесконечного ожидания сайт сразу строит QR официальной платёжной ссылки. Он подписан как **QR платёжной формы Platega**: сканировать камерой телефона, затем подтвердить СБП в форме. Страница ZAL остаётся открытой и продолжает авторизованный polling. Когда GET вернёт проверенный прямой `qr.nspk.ru`, компонент автоматически заменит код и инструкции на банковские. Для прямого банковского QR с первого шага необходим поддерживаемый провайдером способ инициализации для этого мерчанта.

Существующая ссылка сохранена; новые платежи и списания при диагностике не создавались. Callback, ключи и проверка подтверждения не менялись. Валидация QR допускает только точные HTTPS-хосты `qr.nspk.ru` и `pay.platega.io`, без credentials, нестандартных портов и fragment.

Проверка исправления: 13 frontend-тестов, production build; существующий неоплаченный заказ открыт в локальной сборке через production API только для чтения. QR формы PNG 768×768 успешно появился, ссылка оплаты сохранена, на viewport 390×844 переполнения нет. Реальная оплата в диагностике не проводилась.
