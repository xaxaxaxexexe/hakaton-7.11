# Запуск и размещение ZAL

## Что проверено локально

7 ноября 2026: интерфейс `http://localhost:5173` работает с настоящим FastAPI и SQLite на `127.0.0.1:8000`. Старый процесс `scripts/mock_api.py` остановлен. Платёжный провайдер локального окружения — sandbox (`PAYMENT_PROVIDER=mock`), поэтому деньги не списываются и интерфейс показывает демо-режим.

Проверено в браузере: афиша → матч → 3D с места → email → sandbox-оплата → QR-билет. После обновления страницы и полного завершения/повторного запуска процесса API тот же билет доступен. В SQLite один билет на заказ, заказ `paid`, место `sold`. Публичный endpoint проверки QR возвращает `valid` и не раскрывает email. Это подтверждает сохранение данных и интеграцию UI с сервером; реальную банковскую оплату эта проверка не заменяет.

## Локальный запуск

Нужны Python 3.12+, Node.js 22+ и существующий `apps/api/.env`. Заполненный `.env` не перезаписывать; ключи не помещать в frontend или `VITE_*`.

```sh
cd apps/api
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt
PAYMENT_PROVIDER=mock DATABASE_PATH=./data/zal-integration.db \
PUBLIC_APP_URL=http://localhost:5173 PUBLIC_API_URL=http://127.0.0.1:8000 \
ENABLE_EXTERNAL_MEDIA_NETWORK=0 ENABLE_BACKGROUND_RECONCILER=1 \
.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000 --no-access-log
```

В другом терминале:

```sh
cd apps/web
npm ci
npm run dev
```

Vite уже проксирует `/api` в `127.0.0.1:8000`. Для параллельной изолированной проверки API можно использовать порт 8001, указав тот же порт в `PUBLIC_API_URL`; основной frontend тогда продолжит обращаться к 8000.

```sh
cd apps/api
.venv/bin/python -m unittest discover -s tests -v
```

CI выполняет backend-тесты с временными SQLite-базами и фейковыми провайдерами, проверку общего контракта и сборку frontend. Автоматические проверки не создают реальные платежи и не выполняют возвраты.

## Production — размещено

7 ноября 2026, 10:18 UTC: https://cinema.makhkets.ru отвечает HTTP/2 200 с действующим сертификатом. `/api/v1/health` возвращает `mode=live`. Проверены 26 пунктов серверной и публичной приёмки: [отчёт](artifacts/production-api-audit.json). Авторизация Platega с сервера — HTTP 200; реальная банковская покупка пока ожидает ручного подтверждения владельцем.

| Параметр | Значение |
| --- | --- |
| Домен приложения | `https://cinema.makhkets.ru` |
| Сервер | `31.59.190.14`, Ubuntu 24.04 |
| HTTP/TLS | Существующий TLS-сервис на 443 → nginx 127.0.0.1:8080/8081 → API 8100 |
| Процесс приложения | systemd, один Uvicorn worker, `127.0.0.1:8100` |
| Файл конфигурации | `/etc/zal/zal.env`, доступ только владельцу сервиса/root |
| Постоянная SQLite-база | `/var/lib/zal/zal.db` |
| Сборка frontend | `apps/web/dist`, отдаётся приложением или nginx |
| Callback приложения | `/api/v1/payments/platega/callback` |

В `/etc/zal/zal.env` требуются `APP_ENV=production`, `PAYMENT_PROVIDER=platega`, `DATABASE_PATH=/var/lib/zal/zal.db`, `PUBLIC_APP_URL=https://cinema.makhkets.ru`, `PUBLIC_API_URL=https://cinema.makhkets.ru`, `CORS_ORIGINS=https://cinema.makhkets.ru`, `ENABLE_BACKGROUND_RECONCILER=1`, а также приватные `PLATEGA_MERCHANT_ID`, `PLATEGA_API_KEY` и постоянный `ORDER_TOKEN_SECRET`. Значения секретов здесь намеренно не приводятся. Для внешнего каталога iTunes включено `ENABLE_EXTERNAL_MEDIA_NETWORK=1`; ключ не требуется. Основная афиша и тестовое видео остаются локальными.

Сервис работает от системного пользователя `zal`; конфигурация читается systemd из root-only файла. Полный unit: [deploy/zal.service](../deploy/zal.service). Текущий release выбирается симлинком `/opt/zal/current`:

```ini
[Service]
WorkingDirectory=/opt/zal/current/apps/api
EnvironmentFile=/etc/zal/zal.env
ExecStart=/opt/zal/venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8100 --workers 1 --no-access-log
Restart=on-failure
RestartSec=3
```

Перед запуском: установить Python-зависимости, выполнить `npm ci && npm run build` в `apps/web`, создать каталог `/var/lib/zal` с правом записи для пользователя приложения. Не запускать приложение от root. nginx должен передавать запросы на 8100; SPA-маршруты возвращают `index.html`, неизвестные API-маршруты — JSON-ошибку. Для SSE не включать буферизацию.

## Сохранение данных и обновление

Миграции и seed выполняются при запуске. Они не удаляют заказы, оплаты, билеты, активные брони и серверные цены существующих мест. Геометрия без заказов может получить дополнительные места; геометрия с покупкой сохраняется целиком. Изменение купленного матча или удаление кресел требует отдельной миграции.

Перед обновлением сделать согласованную SQLite backup через backup API/команду `.backup`; не копировать только основной файл во время записи, игнорируя WAL. Размещать SQLite на постоянном локальном диске, не в эфемерном контейнере и не в нескольких независимых репликах. Не менять `ORDER_TOKEN_SECRET` после создания заказов: прежние Bearer-токены зависят от него.

## Приёмка production после размещения

1. Проверить HTTPS, открытие страницы и прямых маршрутов `/sessions/...`, `/orders/...`, `/payment/return`.
2. `/api/v1/health` должен вернуть `mode=live`; проверить два стадиона, восемь матчей, актуальные матчи, 282 места.
3. Убедиться, что sandbox-confirm и публичный импорт каталога недоступны.
4. Проверить подтверждение Platega через серверный GET/callback, сопоставление суммы, валюты и заказа. Callback существующего мерчанта не перенастраивать без согласования с другими проектами; фоновая сверка остаётся необходимой.
5. Человек выполняет согласованную реальную покупку. Только после серверного `CONFIRMED` должны появиться `paid`, `sold` и один билет.
6. Перезапустить systemd-сервис, повторно открыть заказ и проверить QR. Повторная обработка статуса не должна выпускать второй билет.

Публичный HTTPS, действующий production callback и реальная покупка считаются проверенными только после отдельной приёмки на размещённом сервере. Демонстрационные площадки в каталоге не обещают право входа в настоящий коммерческий стадион.

## Выпуск следующей версии

Из чистого checkout проверенного `main`:

```sh
npm ci --prefix apps/web
npm run build --prefix apps/web
deploy/release.sh root@31.59.190.14
```

Скрипт отправляет только приложение, fixtures и собранный frontend. Секреты и базы не входят в архив. Он создаёт отдельный release, записывает Git SHA в `REVISION`, переключает симлинк, перезапускает только `zal.service` и проверяет health. При неуспехе возвращает предыдущий код; `/var/lib/zal/zal.db` не перезаписывается. Вход по SSH может использовать ключ либо приватный файл пароля через `ZAL_SSH_PASSWORD_FILE` и установленный `sshpass`. Файл пароля не хранится в репозитории.

Конфигурация nginx — [deploy/nginx.conf](../deploy/nginx.conf). Существующий сервис TLS сохранён: его сертификат теперь содержит IP и `cinema.makhkets.ru`; acme.sh автоматически обновляет оба имени по действующему cron. Сертификат подхватывается горячим обновлением, сторонний сервис не перезапускался. Резервная копия прежнего сертификата хранится только у root в `/root/zal-deploy-backups`.

Callback мерчанта не изменялся. Заказы регулярно сверяются через серверный GET Platega; один worker выполняет сверку каждые 15 секунд, страница заказа также запрашивает актуальный статус.

## Демопокупка и восстановление доступа

`deploy/zal.service` задаёт `DEMO_CHECKOUT_MINOR=100`: новые заказы для всех мест оплачиваются по демотарифу 1 ₽ до комиссии; афиша сохраняет 350/550/900 ₽. В `/etc/zal/zal.env` можно явно поставить 0, чтобы вернуть оплату по полной цене. Старая проверочная сессия сохраняет ID, но её цены афиши обновляются до обычных; заказы, транзакции и брони сохраняются.

7 ноября обнаружена причина недоступности общего IP: Remnanode добавил адрес прокси хостинга `31.59.190.14` в nftables set `ip remnanode torrent-blocker`. Через прямой IP `57.129.28.115` SSH работал. Бан снят, в начало input/forward добавлено исключение `zal-trusted-nat` только для TCP 22/80/443. У остальных адресов защита продолжает работать.

На сервер установлены `deploy/zal-nat-allow.py`, `.service`, `.timer`: таймер каждые 5 секунд восстанавливает исключение при пересоздании таблицы Remnanode и удаляет общий IP из временных source-ban sets. Скрипт расположен в `/usr/local/sbin/zal-nat-allow.py`. Адрес также сохранён в `/opt/mobile443/manual_allow.conf`. Правила до исправления сохранены приватно в `/root/zal-deploy-backups/firewall-before-nat-exception.json`. VPN и TLS процессы не перезапускались.

Это исключение на уровне firewall конкретной ноды; конфигурация плагина в удалённой панели Remnawave не менялась. Если панель полностью пересоздаёт nftables-таблицу, таймер восстановит правило в пределах своего интервала. Нативное исключение плагина находится в `torrentBlocker.ignoreLists.ip`, см. [официальную документацию](https://docs.rw/learn/node-plugins/).

Чат матча использует SSE и историю последних 50 сообщений в памяти. История сбрасывается при перезапуске; SQLite-заказы и билеты сохраняются.
