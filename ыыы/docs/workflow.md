# Ветки и совместная работа

Один репозиторий, две рабочие ветки, общий main. Каждый клонирует весь репозиторий и работает в своей ветке. Оба приложения хранятся рядом, чтобы интеграцию можно было проверить одной версией кода.

## Владение файлами

| Путь | Владелец |
| --- | --- |
| apps/web/** | Makhkets |
| apps/api/**, docs/platega.md, docs/deployment.md | jasperBLCK |
| contracts/**, AGENTS.md, README.md, .github/** | Общие изменения согласовать |

Каждый ИИ получает только промпт своей роли и читает общий контракт. Не поручать обоим ИИ одновременно исправлять один файл контракта.

## Перед началом этапа

~~~sh
git status
git fetch origin
git merge origin/main
~~~

Сначала сохранить свои изменения коммитом. Не применять reset --hard для «синхронизации».

## Закончен небольшой этап

~~~sh
git add apps/web
git commit -m "feat(web): render cinema and session selection"
git push origin frontend
gh pr create --base main --head frontend --title "Выбор стадиона и матча"
~~~

Для бэкенда аналогично с apps/api и backend. В PR указать закрываемые задачи F/B, изменения API, проверки и известные ограничения.

Слияние: Makhkets координирует main, второй участник быстро просматривает изменения. Использовать обычный merge commit, **не squash** для этих долгоживущих веток: история останется общей.

~~~sh
gh pr merge NUMBER --merge
git fetch origin
git merge origin/main
git push
~~~

После каждого merge каждый подтягивает main в свою ветку. Не удалять frontend/backend после PR. Не сливать backend напрямую в frontend и обратно — общий источник main.

## Когда интегрироваться

Первая интеграция через 45 минут, затем после каждого законченного вертикального этапа, ориентир каждые 30–45 минут. Не ждать последних 30 минут.

При несовместимом изменении сначала обновить контракт отдельным PR, указать затронутые поля, затем адаптеры обеих сторон. По возможности добавлять поля без удаления существующих.

## Если конфликт

Владелец файла выбирает итоговую реализацию и проверяет её. Для contracts/** оба сверяют семантику. После разрешения выполнить проверки контракта и сквозной сценарий. Не выбирать целиком ours/theirs для общей схемы без чтения.
